## Фаза 1 — Сразу после диплома

**Цель:** Технический долг и базовые дыры которые мешают реальным пользователям.

### Исторический курс при добавлении / редактировании транзакции
- **Тип:** Android + Backend
- **Суть:** Новый эндпоинт в Currency Service — курс на конкретную дату (`GET /api/v1/rates/history?base=EUR&date=2026-01-15`). При добавлении траты задним числом или при редактировании валюты транзакции — используется курс на дату транзакции, а не текущий.
- **Зачем:** Сейчас пересчёт старых трат идёт по сегодняшнему курсу — это даёт неправильную историю расходов. Курс за 395 дней уже есть в БД, нужен только эндпоинт.
- **Ограничение:** Данные есть только за последние 395 дней (период хранения CERPS). Для более старых дат — fallback на ближайший доступный курс.

### JSON экспорт + импорт из других приложений
- **Тип:** Android
- **Суть:** Экспорт всех данных в стандартный BC-JSON формат через `ActivityResultContracts`. Импорт из популярных приложений — CSV-маппер с выбором источника. Пользователь выбирает "откуда импортируешь" и маппер знает какие колонки брать.
- **Целевые приложения для импорта:** Money Manager, Spendee, Wallet by BudgetBakers (все используют CSV экспорт).
- **Зачем:** Снижает порог перехода с других приложений. Без этого пользователи теряют всю историю при переходе.

### Теги для транзакций
- **Тип:** Android
- **Суть:** Гибкая система тегов на транзакцию. Пример: категория "Рестораны" + тег "работа" или "свидание". Фильтрация по тегам в `UnifiedTransactionListScreen`. Никакой жёсткой иерархии.
- **Технически:** `TagEntity` + junction table `TransactionTagEntity`. Новый фильтр в `UnifiedTransactionListViewModel`.
- **Зачем:** Даёт дополнительное измерение для анализа без усложнения структуры категорий.

### График курсов из внешнего источника (Frankfurter API)
- **Тип:** Backend / Android
- **Суть:** Использовать Frankfurter API (`api.frankfurter.app`) для `RateHistoryScreen` — данные ЕЦБ с 1999 года, бесплатно, без ключа. CERPS остаётся для текущих курсов и конвертации транзакций.
- **Зачем:** Сейчас новый пользователь видит пустые или бедные графики — история накапливается только с момента запуска CERPS. Frankfurter решает это сразу для фиатных пар.
- **Примечание:** Для крипто-пар — CoinGecko (см. Фаза 3).

### UnifiedTransactionListScreen redesign + chart improvements
- **Тип:** Android / UX
- **Суть:** Переработать `UnifiedTransactionListScreen`. Улучшения тренд-графика: интерактивный scrub с детализацией бакета, "перетягивание" категорий по экрану, более компактный список фильтров. На Compact — chart должен схлопываться при скролле списка вниз, разворачиваться при свайпе вверх.
- **Зачем:** Основной "экран анализа" — сейчас функционально мощный, но визуально перегружен. Нужен второй проход по UX.

### RateHistoryScreen: animated search в currency selector
- **Тип:** Android / UX
- **Суть:** В `CurrencyPickerBottomSheet` (используется на `RateHistoryScreen` для выбора валютной пары) добавить анимацию раскрытия поиска: search-icon при тапе плавно превращается в TextField, фокусируется. На пустой строке — возврат к иконке.
- **Технически:** `AnimatedContent` + `FocusRequester`. Сам `CurrencyPickerBottomSheet` живёт в `ui/components/common/` — улучшение распространится на все три экрана-потребителя.
- **Зачем:** Сейчас поиск всегда виден как полноценный TextField — на коротких списках занимает место без надобности. Animated search — стандартный паттерн (Telegram, Material 3 Search Bar).

### Шаблоны + повторяющиеся транзакции
- **Тип:** Android
- **Суть:** Long-press на транзакцию → создать шаблон. WorkManager для автоматического создания по расписанию (подписки, аренда, зарплата). Планируемые будущие транзакции с датой в будущем.
- **Технически:** `TemplateEntity` + `RecurringRuleEntity` (period, next_date). WorkManager `PeriodicWorkRequest`.
- **Зачем:** Подписки и регулярные платежи сейчас нужно вводить вручную каждый раз.

## Фаза 2 — Персонализация

**Цель:** Пользователь настраивает приложение под себя.

### Quick-action кнопки в шапке MainScreen
- **Тип:** Android / UX
- **Суть:** В шапке главного экрана (рядом с балансом) — 3 настраиваемых слота. Каждый можно назначить на любой экран приложения или оставить пустым. Справа — список всех доступных экранов для назначения.
- **Технически:** Массив из 3 `String` (route names) в DataStore. Кнопки читают его и навигируют по route.
- **Зачем:** Разные пользователи используют разные экраны чаще всего; сейчас навигация одинакова для всех.

### Настраиваемые уведомления с AI-текстом
- **Тип:** Android
- **Суть:** Дефолтные уведомления из коробки: "не записывал траты 24ч", "лимит категории близко", "повторяющаяся транзакция сегодня". Каждое можно отключить. Текст уведомления генерирует Gemini — живой, разный каждый раз, не скучный шаблонный. Пример вместо "Вы не записывали траты 24 часа" → "Эй, сегодня ничего не записал. Кофе не считается 👀". Пользователь может задать свой стиль текста.
- **Технически:** WorkManager для расписания. Перед отправкой пуша — вызов Gemini с промптом и контекстом (тип уведомления, язык приложения).
- **Зачем:** Напоминания формируют привычку записывать траты. Живой текст снижает усталость от уведомлений.

### Настройки отображения (Display preferences)
- **Тип:** Android / UX
- **Суть:** Новая секция в Settings. Чекбоксы: скрыть режим "Наличные" если не используешь, скрыть режим "Крипта", округлять баланс до целых, скрыть центы в транзакциях. Хранится в DataStore, применяется глобально.
- **Зачем:** Разные пользователи — разные сценарии. Лишние элементы создают визуальный шум.

### PIN / биометрическая блокировка
- **Тип:** Android
- **Суть:** `BiometricPrompt` API. PIN как fallback. Блокировка при уходе в фон (настраиваемый таймаут: сразу / через 1 мин / через 5 мин). Опционально — скрыть суммы на главном экране без разблокировки.
- **Зачем:** Финансовые данные на телефоне без защиты — частая причина отказа от приложения.

### Онбординг-квиз + профили пресетов
- **Тип:** Android / UX
- **Суть:** 3-4 вопроса при первом запуске → автоматический пресет категорий, банков, валют. Профили: Студент / Путешественник / Экспат / Семья. Уменьшает время до первой транзакции.
- **Зачем:** Сейчас 7-шаговый онбординг требует ручной настройки всего. Квиз определяет контекст пользователя и предзаполняет разумные дефолты.

## Фаза 3 — Расширение охвата

**Цель:** Новые валюты, крипта, новая аудитория.

### Расширение валют — RUB и другие
- **Тип:** Backend
- **Суть:** Исследовать и подключить провайдеров для валют которые сейчас не поддерживаются. RUB: CBR API (официальный курс ЦБ) или MOEX как источник рыночного курса. Также BYN (НБ РБ API), GEL, AMD, AZN. Увеличить покрытие с 18 до 30+ валют.
- **Зачем:** Целевая аудитория — СНГ-эмигранты. RUB критичен для значительной части пользователей.
- **Сложность:** После 2022 большинство западных провайдеров не дают RUB или дают нерыночный курс. CBR API — официальный но не рыночный. MOEX — ближе к реальному но нестабильная доступность из EU.

### Crypto-service в CERPS
- **Тип:** Backend
- **Суть:** Отдельный микросервис (порт 8084) на CoinGecko API. Эндпоинты: текущие курсы топ-монет, история по дням за любой период. Архитектурно параллелен Currency Service — без смешивания фиата и крипты в одной БД.
- **API:** CoinGecko — бесплатно, без ключа на базовом плане, 30 запросов/мин, история за любой период.
- **Зачем:** Основа для крипто-счетов и оплаты криптой в Android-приложении.

### Счета в крипте + оплата криптой
- **Тип:** Android
- **Суть:** `AccountEntity` с `currency = "BTC"` / `"ETH"` / `"USDT"`. Третий режим в форме транзакции: Карта / Наличные / Крипта. Баланс хранится в крипто-единицах (`originalAmount`), конвертируется в базовую валюту через crypto-service. График истории BTC/EUR по дням в `RateHistoryScreen`.
- **rateSource:** добавить `CRYPTO_RATE` в перечень.
- **Зачем:** Крипто-пользователи сейчас не могут учитывать реальные расходы в крипте. Архитектурно вписывается в существующую логику счетов.

## Фаза 4 — Финансовое планирование

**Цель:** Накопления, бюджеты, обязательства.

### Накопления (Goals)
- **Тип:** Android
- **Суть:** Специальный тип счёта с целевой суммой и дедлайном. "Накопить 3000€ к июню". Приложение считает сколько нужно откладывать в месяц, рисует прогресс-бар. Переводы на Goal-счёт фиксируются как "отложено".
- **Технически:** `AccountEntity` + поля `goalAmount: Double?` и `goalDate: Long?`. Отдельный тип `AccountType.GOAL` для UI.
- **Зачем:** Накопления — основной сценарий после контроля расходов. Многие приложения строятся именно вокруг этого.

### Конверты (Envelope budgeting)
- **Тип:** Android
- **Суть:** Распределяешь доход по конвертам в начале месяца. Конверт "Еда" = 400€, включает категории "Продукты" + "Рестораны". Деньги реально резервируются — не просто потолок. Работает параллельно с лимитами категорий: пользователь выбирает что использовать.
- **Технически:** `EnvelopeEntity(id, name, budgetAmount, periodType)` + junction table `EnvelopeCategoryEntity`. Отдельный экран "Бюджет месяца".
- **Разница с лимитами:** Лимит — это потолок ("не трать больше X"). Конверт — это реальный резерв из дохода ("у тебя есть ровно X из этого дохода"). Психологически работает сильнее.

### Кредиты и ипотека
- **Тип:** Android
- **Суть:** Специальный тип счёта с отрицательным балансом. Поля: сумма долга, процентная ставка (годовых), срок (месяцев), дата первого платежа. Приложение рассчитывает ежемесячный платёж (аннуитет), показывает сколько осталось, сколько переплатишь, разбивку каждого платежа на тело + проценты.
- **Технически:** `AccountType.LOAN` + `LoanDetailsEntity(accountId, totalAmount, annualRate, termMonths, startDate)`.
- **Зачем:** Ипотека и кредиты — реальность для большинства взрослых пользователей. Без учёта обязательств картина финансов неполная.

### Расширенная аналитика
- **Тип:** Android
- **Суть:** Расходы как % от дохода за период. Прогноз трат до конца месяца по текущему темпу. Сравнение периодов (этот месяц vs прошлый, в % и абсолюте). Аномалии — уведомление когда трата в категории необычно крупная относительно среднего.
- **Зачем:** Текущая аналитика показывает что было. Нужно показывать куда движется.

### Учёт способа оплаты для всех транзакций
- **Тип:** Android
- **Суть:** Сейчас `paymentMethod` (Card / Cash / Crypto) фактически известен только когда транзакция мультивалютная — выбор берётся из режима в форме (Card / Cash). Для same-currency транзакций способ оплаты не сохраняется. Сделать `paymentMethod` явным полем `ExpenseEntity` / `IncomeEntity` (или будущей `TransactionEntity`), задавать его всегда — даже когда валюта траты == валюта счёта.
- **Технически:** Новое поле `paymentMethod: String` (enum: `CARD`, `CASH`, `CRYPTO`) в обеих транзакционных таблицах. Дефолт при миграции — `CARD` для существующих записей (наиболее вероятный сценарий). Миграция бэкфилит на основе `rateSource` где возможно (`CASH_EXCHANGE` → `CASH`).
- **Зачем:** Без этого аналитика по способу оплаты (см. ниже) не работает для основной массы транзакций — same-currency расходы это типичный сценарий для большинства пользователей.

### Аналитика по способу оплаты
- **Тип:** Android
- **Суть:** Новые виджеты на `StatisticsScreen`: сколько потратил картой vs наличными vs криптой за период; динамика во времени; топ-категории на наличку. Может стать триггером для финансовых выводов ("90% трат картой — может, проще закрыть один счёт").
- **Зависимость:** требует [Учёт способа оплаты для всех транзакций](#учёт-способа-оплаты-для-всех-транзакций) — иначе нечего агрегировать.
- **Зачем:** Способ оплаты — одна из реальных осей анализа расходов, которая сейчас игнорируется. Особенно важно для пользователей с активным cash flow (путешествия, экспаты).

## Фаза 5 — Социальные и облачные фичи

**Цель:** Требуют авторизации — большой архитектурный сдвиг. Делать блоком после стабилизации фаз 1-4.

### Переводы между счетами
- **Тип:** Android
- **Суть:** `TransferEntity` с сохранением курса обмена на момент перевода. Перевод не создаёт фантомный расход и доход — это отдельный тип операции.
- **Технически:** Триггер для Stage C — объединение `ExpenseEntity` / `IncomeEntity` в единую `TransactionEntity` с discriminator `kind`. Откладывалось именно до этого момента.
- **Зачем:** Без этого перевод с Revolut на SEB создаёт фантомный расход на одном счёте и фантомный доход на другом.

### Google auth + облачный бэкап
- **Тип:** Backend + Android
- **Суть:** Google Sign-In, JWT на CERPS. Зашифрованный бэкап данных Room в облако. Восстановление на новом устройстве. Основа для семейного бюджета.
- **Зачем:** Смена телефона сейчас = потеря всей истории. Это блокер для долгосрочного использования приложения.

### Семейный / совместный бюджет
- **Тип:** Backend + Android
- **Суть:** Shared workspace с приглашением по ссылке. Общие категории, лимиты и конверты. Видимость чужих транзакций настраивается (полная / только итоги / скрыта). Требует Google auth как пресусловие.
- **Зачем:** Семьи и пары не могут видеть совместные расходы в одном месте.

### Авто-импорт из push-уведомлений банков
- **Тип:** Android
- **Суть:** `NotificationListenerService` перехватывает банковские пуши. AI-парсинг суммы, валюты, магазина через Gemini. Предлагает готовую транзакцию пользователю — он подтверждает или редактирует одним тапом. Не заменяет ручной ввод, а дополняет.
- **Зачем:** Снижает трение при большом количестве трат. Сохраняет осознанность через подтверждение — не автоматический импорт.

### Play Store публикация
- **Тип:** UX / Инфра
- **Суть:** App signing, privacy policy, скриншоты для всех размеров экранов (phone, tablet). Closed testing → open testing → production. ASO — ключевые слова и описание на EN/RU. Настроить обработку отзывов.
- **Зачем:** Реальные пользователи дают реальный фидбек. Без публикации проект остаётся дипломной работой.

### CERPS CLI + Render.com deploy
- **Тип:** Инфра
- **Суть:** CLI-утилита для администрирования CERPS без curl (добавить ключ, обновить курсы, сбросить кеш). `render.yaml` для альтернативного деплоя на Render.com как замена Railway при превышении лимитов бесплатного тира.
- **Зачем:** Railway free tier имеет потолок. Нужна стратегия выхода.
